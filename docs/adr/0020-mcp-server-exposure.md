# ADR-0020: Expose existing REST endpoints as an MCP server

- **Status:** Accepted
- **Date:** 2026-09-28
- **Related:** ADR-0004 (review queue - the mutating tools this ADR
  exposes), ADR-0012 (document-chunk search - the read-only tool this ADR
  exposes), ADR-0019 (agent orchestration - the LangGraph agent is a
  natural first consumer of this MCP server, though this ADR does not
  depend on that one shipping first)

## Context

Skills-map has carried `MCP server ⏳ P3` as a placeholder since early
in the project ("MCP is a term in the game" was the only prior claim on
it) - it's a named gap, not a new idea. Cluster A's postings (agentic RAG
in regulated finance) name MCP/A2A-compliant interfaces specifically, as
a way agents interoperate across tools/teams rather than every team
hand-rolling its own tool-calling contract per agent.

Term Rush already exposes the right shapes as ordinary REST endpoints:

- `GET /terms/random`, `GET /terms/categories`, `GET /terms/{id}/stats`
  (`game_service/api/routers/terms.py`) - read-only term-bank queries.
- `GET /document-chunks/search` (`game_service/api/routers/document_chunks.py`)
  - read-only semantic search over the RAG corpus (ADR-0012).
- `GET /review-queue`, `POST /review-queue/{id}/approve`,
  `POST /review-queue/{id}/reject` (`content_service/api/routers/review_queue.py`)
  - the human-in-the-loop gate ADR-0004 already established, with two of
    the three operations *mutating* (approve promotes a candidate into
    the live term bank; reject discards it permanently).

The question this ADR answers is narrow: how does an MCP client (Claude
Code, the LangGraph agent from ADR-0019, or any other MCP-speaking tool)
reach these, and which of them should it be allowed to reach.

## Decision

**Use `fastapi-mcp` to auto-generate MCP tools from the existing FastAPI
routers, mounted read-only by default; mutating review-queue operations
are exposed as separate, explicitly-opted-in tools gated behind the same
auth the REST API would require for a human to call them.**

Two auto-generation approaches exist (`fastapi-mcp`, mounting directly onto
a live app with five-minute setup; FastMCP's `from_fastapi()`, generating
from the OpenAPI spec). This project already generates a typed client from
its OpenAPI schema for the web frontend (`just generate-client`) - the
same schema-as-contract instinct applies here. `fastapi-mcp` is chosen
over hand-writing a parallel tool-definition file (the way `enrich.py`'s
`DRAFT_TERM_TOOL` is hand-written) because these tools *are* the existing
REST contract, not a new one designed for the LLM's convenience - drift
between "the API" and "the MCP tools" would be a second schema to keep in
sync for zero benefit.

**Scope, by risk:**

- **Read-only, exposed by default:** `get_random_term`,
  `get_term_categories`, `get_term_stats`, `search_document_chunks`,
  `list_review_candidates`. These can't change state; the worst a
  malicious or confused agent does is waste a call.
- **Mutating, exposed but separately gated:** `approve_review_candidate`,
  `reject_review_candidate`. `fastapi-mcp` supports filtering which
  operations become tools by tag/operation-id - these are tagged
  distinctly so a deployment can mount the read-only set without the
  mutating set at all, matching the security guidance that authorization
  is checked per tool call, not just per connection. In practice: the
  LangGraph agent from ADR-0019 gets the read-only set only; approval
  stays a human action through the existing review-queue UI, full stop.
  An agent drafting candidates for review is the point (ADR-0004,
  ADR-0019); an agent approving its own drafts defeats the human-in-the-
  loop gate that both of those ADRs exist to establish.
- **Auth:** inherits FastAPI's existing middleware stack (per
  `fastapi-mcp`'s design) rather than a parallel auth mechanism. ADR-0014's
  JWT plan, once implemented, covers this the same way it covers the REST
  API - no separate MCP-specific credential to provision or rotate.

## Consequences

**Good:**

- Zero new tool-schema surface to maintain - the OpenAPI schema already
  regenerated by CI (`just generate-client`'s check) is the same source
  of truth an MCP client sees
- The read/mutate split is a real, defensible security decision
  ("agents draft, humans approve") that directly answers what a
  regulated-domain interviewer would ask first: "can the agent approve
  its own output?"
- Reuses ADR-0014's planned auth instead of inventing MCP-specific
  credentials - one identity story, not two

**Bad:**

- `fastapi-mcp` is a third-party wrapper, not the MCP reference SDK
  directly - if it lags behind an MCP spec revision, this project inherits
  that lag rather than controlling its own upgrade timing
- Auto-generated tool descriptions come from existing docstrings/schemas
  written for human API consumers, not tuned for how well an LLM
  interprets a tool description - may need targeted rewording once real
  agent usage shows where tool selection goes wrong
- Read-only "by default" is a policy this ADR states, not something
  `fastapi-mcp` enforces on its own - the tag-based filtering has to
  actually be applied and tested, or the split is just a comment

## Alternatives considered

**Hand-write MCP tool schemas** (the `enrich.py` `DRAFT_TERM_TOOL`
pattern, one per endpoint). Rejected: doubles the schema surface for
endpoints that already have a perfectly good Pydantic-backed OpenAPI
schema; the only reason `enrich.py` hand-writes one is that its tool
(`draft_term`) has no corresponding REST endpoint to derive from.

**Expose everything, including approve/reject, and rely on the LangGraph
agent's own prompt to "never approve without asking."** Rejected: prompt
instructions are not an authorization boundary (ADR-0013 already commits
this project to that position for player-input handling); relying on the
model to decline a tool call it's technically permitted to make is exactly
the "confused deputy" pattern current MCP security guidance warns against.

## When I would change this

- If a second agent consumer (beyond ADR-0019's LangGraph graph) needs
  the mutating tools for a workflow that genuinely has no human in the
  loop, that's a new ADR justifying *that* exception specifically - not a
  reason to widen this one's default.
- If `fastapi-mcp`'s tag-based filtering proves insufficient for a finer-
  grained policy (e.g., per-candidate-confidence gating on approval),
  revisit whether the mutating tools need their own dedicated router
  rather than a filtered view of the existing one.
- If ADR-0014's auth lands with a scope/permission model, revisit whether
  MCP tool access should be scoped per-token rather than per-deployment
  (today's read-only-by-default is a deployment-time choice, not a
  runtime one).
